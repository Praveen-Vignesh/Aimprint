# AUDIT-2026-10 — pre-collection hardening

A full read of `schema.sql`, `src/`, and every markdown file, done immediately before the
one-off data-collection campaign (20 humans + 5 bot variants, ~150 sessions). The database held
2 subjects and no real data at audit time, which is why format-breaking and append-only-breaking
fixes were taken now rather than deferred — after collection they would be unrecoverable, because
the telemetry is the deliverable and cannot be re-collected.

The architecture was found sound: the subject/session/segment split, append-only RLS, the
three-valued default-deny label with retroactive relabelling, and the outbox idempotency contract
are all correct and were preserved. Every change below makes the database or client enforce what
the design already intended; none changes gameplay.

Each entry: **what it is · how it fails · why it matters here · the fix · where**.

## Fixed — correctness / data-integrity

### 1. The database trusted the client on server-written columns · `schema.sql` C.1
- **What:** RLS gates which *rows* an account may insert, never which *columns*. `sessions`
  documented `started_at`, `poll_hz`, `ended_at` (and the since-dropped `bot_mode`) as "server-written, never
  client-supplied", and `segments.created_at` likewise — but all were client-writable.
- **How it fails:** a hand-crafted REST insert could forge `started_at` (ordering is used for
  fatigue effects and replay detection) or `created_at` (the archive job's and the incremental
  pull's ordering key).
- **Why here:** biometric timing data whose timestamps are forgeable is not trustworthy ground
  truth.
- **Fix:** `revoke insert` then column-level `grant insert (…)` on `sessions` and `segments`,
  excluding the server columns, mirroring the existing `profiles` UPDATE grant. `sessions.id` is
  granted so the client can mint the session uuid (see #6).
- **New hazard this creates (documented loudly in `schema.sql` and `CLAUDE.md`):** a client
  column added to the payload but not to the grant fails with `42501`, which the outbox treats as
  permanent and drops. The matching client change — removing `poll_hz` from the session payload —
  is in `src/telemetry.js`.

### 2. Consent was enforced only in JavaScript · `schema.sql` C.2
- **What:** `canPlay()` / `applyStartGate()` check consent client-side; the `sessions` insert
  policy did not.
- **How it fails:** a REST insert bypassing the UI could store telemetry from an account that
  never consented.
- **Why here:** the data is collected under a consent notice; that precondition belongs in the
  database.
- **Fix:** new `current_consent_version()` (SECURITY DEFINER, empty search_path); the insert
  policy now requires `(select public.current_consent_version()) is not null`. Existence, not
  version match — version currency stays a client concern.

### 3. `merged_into` resolved only one level — SUPERSEDED, feature removed 2026-10-17
- **What it was:** the training view collapsed duplicate identities with
  `coalesce(merged_into, subject_id)`, which resolves exactly one hop, so `A→B→C` left A and C on
  different identities — one person on both sides of a `GroupKFold` split.
- **Original fix (2026-10-11):** a self-reference CHECK plus an `enforce_merge_depth` trigger
  pinning the chain depth at ≤1 in both directions.
- **Superseded:** the entire merge mechanism was **removed** — `merged_into`, its CHECK, the
  trigger, its function and `subjects_merged_into_idx` are all gone, and the view no longer
  collapses anything. One subject row is now one identity, full stop. A duplicate is handled by
  **excluding the extra account** at labelling time, which is viable because the cohort is ~25
  hand-recruited contributors labelled by email.
- **Note for the future:** requiring an account does **not** prevent duplicate identities (one
  person can hold two emails). The small, personally-known cohort is what makes this safe — if
  the project ever opens to public signups, the merge mechanism has to come back.

### 4. A failed `sessions` insert discarded the whole session · `src/supabase.js`, `src/game.js` D.1
- **What:** `insertSession()` returned `null` on failure; `insertSegment()` then returned before
  enqueuing, so every segment for that run was discarded before reaching the outbox or IndexedDB.
  A quieter second loss: segments recorded before the session id resolved lived only in memory.
- **How it fails:** one transient 5xx at the start of a run — exactly when contention is highest —
  cost a whole participant session, reported only to the user's own `console.warn`.
- **Why here:** unregenerable data lost invisibly.
- **Fix:** `game.start()` mints the session uuid (`crypto.randomUUID`, with a fallback) so segments
  enqueue synchronously against a known id; the session row goes to its own durable outbox +
  IndexedDB store and is retried; `23503` (FK-not-yet) is reclassified transient so a segment that
  reaches the DB before its session row waits rather than being dropped.
- **Verified:** headless harness — a segment reaches the delivery layer with the minted id even
  when `insertSession` fails.

## Fixed — delivery / durability

### 5. No shape validation on segment rows · `schema.sql` C.4
CHECKs assert each stated count matches its array (`targets`/`target_count`,
`trajectory.t`/`frame_count`, `input_events.dt`/`event_count`, `engaged_index` in range). A fifth
guarded `board_trajectory.x`/`target_count` and went with that column when it was removed
(2026-10-17). The `?` key-existence test is load-bearing — `jsonb_array_length(null)`
is null and a null expression *satisfies* a CHECK, so a blob missing its key would otherwise pass.
Catches a telemetry assembly bug at write time instead of months later in the pipeline.
All are **`NOT VALID`**: the live table already holds pre-v4 rows whose `input_events` is the
old `{t, dx, dy}` shape (no `dt` key), so a `VALID` add fails the scan of history (hit on the first
migration run, 2026-10-11). `NOT VALID` enforces the shape on every future write — all v4 and
conforming — while grandfathering the old rows, which are excluded from a v4 pull by
`sampling_version` and pruned anyway. Do not `validate constraint` them while any pre-v4 row
remains.

### 6. `FLUSH_DEBOUNCE_MS` made the batch size effectively 1 · `src/outbox.js` D.2
Tracking emits ~1 segment/second and the debounce was 400 ms, so every row shipped alone (~300
POSTs per 5-min session). Raised to 5000 ms (~5 rows/request); no added risk, since rows are
persisted on enqueue and flushed on pause / run-end / unload.

### 7. A shared machine dropped the previous participant's queued rows · `src/outbox.js`, `src/supabase.js` D.3
Undelivered rows live in the browser; if participant B signed in while A's rows were queued, the
DB refused A's rows (`42501`) and the outbox dropped them permanently. Now each queued row carries
its owning `user_id` in the IndexedDB envelope (never in the row), and a row whose owner is not the
signed-in user is **held, not attempted** — delivered when that owner returns.

### 8. The keepalive flush was silently over the browser limit · `src/outbox.js`, `src/supabase.js` D.4
`flushKeepalive()` sent every pending row in one `fetch(keepalive:true)`; browsers cap that body at
~64 KiB and two segments already exceed it, so the "last best-effort delivery on unload" promise
was largely false. Now it fills one request to a ~60 kB budget, oldest first, and leaves the rest
to replay. (Nothing was lost before — rows replay next load — but the docs claimed otherwise.)

### 9. `validateSession()` was not awaited before the outbox started · `src/main.js` D.5
It was called before `initTelemetryOutbox()` but not awaited, so the outbox could replay under a
session about to be invalidated. Now chained with `.finally`, and owner-scoping (#7) makes a replay
under a just-signed-out identity safe regardless.

## Fixed — dataset hygiene

### 10. Multi-target routines wrote misleading rows · `src/routines/index.js` B
`gridshot` and `switching` use `aimTarget() → pool.active[0]`, an arbitrary target, so
`trajectory.tx/ty/tz` and `engaged_index` describe a target the player may not be aiming at, and
nothing records which target was struck. Rather than feed plausible-but-wrong rows into the
dataset, both routines are **withheld** (absent from the catalogue, `isAvailable()` false) while
all their code — factories, routine files, `difficulty.js` entries — is retained for revival. The
schema keeps `engaged_index`/`target_count` and their guards for that day. **Update
(2026-10-17):** `board_trajectory` was dropped, since `switching` was the only routine that ever
wrote it. Reviving `switching` for data collection now also means re-adding that column, its
shape guard, its lz4 line, its insert-grant entry and the `sampleBoard`/`toBoardColumnar`
plumbing — see the note left in `src/routines/switching.js`.

### 11. `routine` / `difficulty` were unconstrained free text · `schema.sql` C.5
A typo would mint a silent cohort that splits the dataset. Allowlist CHECKs added;
`gridshot`/`switching` kept in the `routine` list since the code still exists.

### 12. Storage would exhaust Free tier mid-campaign · `src/telemetry.js`, `STORAGE.md` D.6, A
`input_events` delta-encoded, `tx/ty/tz` omitted for static routines, `SAMPLING_VERSION` → 4
(~8.5 → ~2.6 MB per 5-min session, lossless). Combined with 5-minute sessions and the
archive-then-prune model (`STORAGE.md`), the ~400 MB campaign fits Free with the staging table
kept under ~150 MB by periodic archiving. Session default dropped 10 → 5 min; the 1-min option
removed.

## Fixed — operability

### 13. `search_path` on SECURITY DEFINER functions · `schema.sql` C.6
`handle_new_user`, `current_subject_id`, `mirror_consent_to_subject` (and the two new functions)
moved from `set search_path = public` to `= ''`. All references are schema-qualified, so this is a
safe close of the standard temp-schema shadowing vector on elevated-privilege functions.

### 14. The training pull could not be incremental or safely paged · `schema.sql` C.7
BRIN index on `segments.created_at` (append-only ⇒ perfectly correlated with physical order, a few
kB, no hot right-edge page). The view now exposes `segment_created_at`, `session_ended_at`,
`subject_consent_version`, and its header documents keyset pagination, the sargable
`subject_kind in (…)` filter (vs the non-sargable `is_human is not null`), the watermark lag, and
that after archival the view is only the un-archived tail.

### 15. Re-running `schema.sql` could strand a signup with no profile · `schema.sql` C.8
The drop/recreate of `on_auth_user_created` has a window; an account created in it would have no
subject/profile and silently drop all its telemetry forever. The idempotent orphan-repair block
(formerly deferred in `src/TODO.md`) now runs after the trigger.

### 16. `archive_manifest` + autovacuum tuning · `schema.sql` C.9
New permanent, service-only table indexing the archive (carries `raw_subject_id`, never a resolved
label, so relabelling stays retroactive). TOAST autovacuum scale factor lowered for the rolling-
buffer churn.

## Follow-up — four always-empty columns removed (2026-10-17)

A later pass identified every column that no code path ever wrote and removed four of them. All
four were verified empty-by-construction against the client (`telemetry.js`, `main.js`) first.

| Dropped | Was | Why removed |
|---|---|---|
| `subjects.merged_into` | duplicate-identity merge pointer | Merging dropped entirely; see the superseded finding #3 above. Took its CHECK, trigger, function and index with it. |
| `profiles.display_name` | always NULL | Nothing wrote it, nothing read it, no UI collected it, and the column grant never made it writable. Resolves the open question in `src/TODO.md` §4. |
| `sessions.bot_mode` | legacy in-browser Bot Mode flag | Bot Mode was removed long ago; the label lives on `subjects.kind`. The `and bot_mode is null` clause came out of the sessions insert policy with it. |
| `segments.board_trajectory` | non-engaged targets' per-frame paths | Only the withheld `switching` routine ever wrote it, so every row had it NULL. |

**Two ordering traps this exposed, both now handled in `schema.sql`:**
1. `v_training_segments` selected `merged_into` and `board_trajectory`, and Postgres refuses to
   drop a column a view depends on. An **early `drop view if exists`** was added near the top of
   the file, above every `drop column`; without it the whole one-buffer run rolls back.
2. The lz4 block shares **one** exception handler, so leaving the dead `board_trajectory`
   compression line in it would have raised inside the block and silently rolled back the
   `trajectory` and `input_events` compression too, reporting only "lz4 unavailable".

**Deliberately kept:** `movesTargets` (and `trajectory`'s `tx/ty/tz` branch). It is easy to
mistake for the removed board plumbing, but it drives the *engaged* target's per-frame position
and `strafing` — a shipping routine with a moving target — depends on it. Removing it would
silently destroy that routine's tracking-error signal. A harness assertion now guards this.

## Accepted risks (deliberately not fixed)

- **`consent_version` text is client-writable.** A signed-in user forging it is consenting to
  something — self-defeating. A CHECK on the string buys nothing.
- **An authenticated subject can POST fabricated trajectories to their own session.** RLS allows a
  user to insert their own rows; it cannot verify the numbers are real human movement. Mitigated by
  labelling only trusted contributors `human` — the label, not the row, is the trust boundary.
- **`device_fingerprint` is a train/test leakage vector.** If bots and humans run on visibly
  different hardware, a model can learn the hardware. `model/DESIGN.md` prescribes training with
  and without the hardware block and comparing — this matters more now that biometric
  identification is in scope.

## Known-remaining (scheduled, not blocking)

- **No ingest observability from the server side.** Every client failure path is a `console.warn`
  in the user's browser. The `queries/campaign.sql` SQL answers "is data landing" from the DB
  side; a client-side `client_events` table is deferred (`src/TODO.md` 4c).
- **`segments.id` is a random UUIDv4** (scatters inserts). Irrelevant at ~45k rows; UUIDv7 noted
  in `src/TODO.md` for any larger future.
- **`input_events` `t0` can be slightly negative** when a coalesced pointer sample's timestamp
  predates its segment's start; harmless (reconstruction is still monotonic), noted for the codec.
- **Archive + Postgres are two systems for consent withdrawal.** The `archive_manifest` is the
  index that makes a withdrawal runbook (delete rows, Storage object, local Parquet) tractable;
  the runbook itself is written when the first withdrawal happens.
- **A session that can never deliver (null auth at a start despite `canPlay`) causes bounded
  infinite retry of its segments.** Backed off to 30 s; owner-scoping clears it on sign-out. Rare
  (the game requires a consented, signed-in account to start).

## Explicitly NOT defects (so they are not "rediscovered")

- No predictions table yet — correct; it is built only once a model exists and must never share a
  column with verified ground truth.
- No labelling RPC/helper — rejected on purpose; PostgREST would auto-expose it to the browser-
  inlined key. Labelling is manual, service-key only (`LABELING.md`).
- The landing page sharing no CSS with `style.css` — intentional payload split, not drift.

  failed session insert with the minted id; static routines omit `tx/ty/tz`; the sanitiser folds

- **Schema:** structural only (balanced dollar-quotes, 9 do-blocks, 5 functions, 3 triggers, all

  buffer, then run `LABELING.md` §6, the orphan query, the grant/negative-insert checks, and an

## Follow-up — finalisation pass (2026-10-18)

Data wiped and `schema.sql` rewritten as one from-scratch DDL file (no longer a
migration — see its header). In the same pass:
- **Consent removed entirely** (supersedes #2): both column pairs, the mirror
  trigger, `current_consent_version()`, the insert-policy clause, the
  `profiles update own` policy, and the client/UI consent flow. Agreement is now
  part of creating an account.
- **All shape CHECKs validated inline** (supersedes the #5 `NOT VALID` note): the
  table is created empty, so there are no pre-existing rows to grandfather; the
  manual `validate constraint` step is gone.
- **`SESSION_MIN_PLAY_MS` gate**: a run under 60 s writes nothing (session row
  and segments buffered then discarded together); results screen says so.
- **`ended_at` dropped; `poll_hz` derived offline.** (A brief client-close design via a
  single-shot UPDATE policy was reverted the same day — nothing consumes `ended_at`, and
  `poll_hz` is computed with the service key by `queries/campaign.sql` §5 / the archive job.
  `sessions` is strictly append-only: no UPDATE policy anywhere.)
- **`sampling_version` reset to 1**; `archive_manifest.raw_subject_id` → `subject_id`.

## Pre-collection production-readiness sign-off (2026-10-18)

A final read-through before real collection, checking every column for the
`ended_at`-class defect (no writer, or no reader) and the client↔grant alignment.

**Verdict: the schema is production-ready. No code change required.**

- **Client ↔ grant aligned.** `sessionInfo()` → `buildSessionPayload` (`src/main.js`,
  `src/telemetry.js`) sends exactly the 19 INSERT-granted `sessions` columns — including
  `screen_height`, `device_pixel_ratio`, `app_version`, `sampling_version` — so there is no
  silent-NULL hardware field and no ungranted column that would `42501` the whole insert.
  `segments` likewise sends exactly its granted set.
- **`poll_hz` is the one column with no automatic writer** — NULL until `queries/campaign.sql`
  §5 (or the future archive job) runs. Intentional, same *class* as the old `ended_at` problem
  but by design. **Run §5 before training**, or train accepting NULL `poll_hz`.
- **`session_metrics` and `archive_manifest` are fully dormant** — no code writes or reads
  either yet (both await unbuilt pipeline code). Expected.
- **Structure is coherent:** valid one-shot execution order, RLS on all six tables, **5
  policies / 0 UPDATE / 0 DELETE**, all CHECKs validated inline, view is `security_invoker` and
  revoked from `anon`/`authenticated`.

**Before collecting, one thing MUST be confirmed:** the live database is one-shot
create-from-scratch and changed after this file's earlier state, so the live DB likely does not
match it. Run **`queries/schema_parity.sql`** and re-apply (teardown + recreate, or the targeted
delta in that script's header) until it is clean. Do not trust the `LABELING.md` STATUS claim of
"applied 2026-10-18" until parity confirms it.
